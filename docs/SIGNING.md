# راهنمای امضای نسخه Release با Keystore اختصاصی

## ریشه مشکل «App not installed as package conflicts with an existing package»

اندروید فقط زمانی اجازه نصب آپدیت روی نسخه قبلی را می‌دهد که **امضای هر دو APK یکسان** باشد.
در بیلد قبلی، اگر Keystore معرفی نشده بود، Gradle بی‌سروصدا از **کلید debug** استفاده می‌کرد.
کلید debug روی هر سیستم/رانر CI به‌صورت خودکار و **متفاوت** ساخته می‌شود؛ در نتیجه هر نسخه جدید
امضای متفاوتی داشت و کاربر مجبور بود اول نسخه قبلی را حذف کند.

**راه‌حل:** همه نسخه‌های Release باید با **یک Keystore خصوصی و ثابت** امضا شوند.

---

## قدم ۱ — ساخت Keystore اختصاصی (فقط یک بار)

روش خودکار (پیشنهادی):

```bash
bash scripts/generate-keystore.sh
```

این اسکریپت:
- فایل `release.keystore` را با کلید RSA-4096 و اعتبار ۳۰ سال می‌سازد،
- فایل `keystore.properties` را کنار پروژه ایجاد می‌کند تا Gradle به‌صورت خودکار آن را بخواند.

روش دستی (معادل همان کار):

```bash
keytool -genkeypair -v \
  -keystore release.keystore \
  -alias aether-release \
  -keyalg RSA -keysize 4096 \
  -validity 10950 \
  -dname "CN=Aether Mobile, OU=Release, O=Aether"
```

سپس فایل `keystore.properties` را در ریشه پروژه بسازید (نمونه: `keystore.properties.example`):

```properties
storeFile=release.keystore
storePassword=رمز-شما
keyAlias=aether-release
keyPassword=رمز-شما
```

> ⚠️ **بسیار مهم:**
> - از `release.keystore` نسخه پشتیبان امن بگیرید. **اگر گم شود، دیگر هرگز نمی‌توانید آپدیت منتشر کنید** و همه کاربران باید حذف/نصب مجدد کنند.
> - این دو فایل هرگز نباید وارد git شوند (در `.gitignore` قرار گرفته‌اند).

## قدم ۲ — بیلد نسخه امضاشده

```bash
./gradlew assembleRelease
```

همین. Gradle به‌ترتیب این منابع را می‌خواند:
1. `keystore.properties` (بیلد محلی)
2. متغیرهای محیطی `KEYSTORE_PATH` / `KEYSTORE_PASSWORD` / `KEY_ALIAS` / `KEY_PASSWORD` (مخصوص CI)

اگر هیچ‌کدام موجود نباشد، بیلد همچنان انجام می‌شود اما یک **WARNING صریح** چاپ می‌شود که خروجی با کلید debug امضا شده و قابل آپدیت نیست (دیگر هیچ فallback بی‌صدایی وجود ندارد).

خروجی‌ها: `app/build/outputs/apk/release/`

برای اطمینان از امضا:

```bash
apksigner verify --print-certs app/build/outputs/apk/release/app-universal-release.apk
```

## قدم ۳ — تنظیم GitHub Actions (انتشار واقعی)

ورک‌فلو `.github/workflows/build.yml` از قبل از Secrets پشتیبانی می‌کند. در تنظیمات ریپو
(Settings → Secrets and variables → Actions) این ۴ مقدار را تعریف کنید:

| Secret | مقدار |
|---|---|
| `KEYSTORE_BASE64` | خروجی `base64 -w0 release.keystore` |
| `KEYSTORE_PASSWORD` | رمز Keystore |
| `KEY_ALIAS` | `aether-release` |
| `KEY_PASSWORD` | رمز کلید |

> نکته: مکانیزم فعلی CI که در نبود Secrets یک «CI keystore» را داخل ریپو ذخیره می‌کند فقط مشکل
> آپدیت‌پذیری را حل می‌کند؛ چون آن فایل عمومی است، **اصالت (Authenticity) ندارد**. برای انتشار واقعی حتماً Secrets را تنظیم کنید.

## مهاجرت کاربران فعلی (یک بار)

کاربرانی که نسخه امضاشده با کلید debug را نصب دارند، برای اولین نسخه با کلید جدید باید **یک بار**
حذف/نصب کنند (اندروید تعویض کلید امضا را اجازه نمی‌دهد). از این به بعد همه آپدیت‌ها بدون حذف نصب می‌شوند.

## امضای ثابت از نسخهٔ ۱.۲.۱ به بعد — هیچ کاری لازم نیست انجام دهید ✅

خبر خوب برای کاربران مبتدی: در همان اجرای قبلی GitHub Actions، خود CI یک کلید امضا ساخته و
آن را به‌صورت خودکار داخل مخزن شما در مسیر `.github/ci-keystore.jks.b64` ذخیره (کامیت) کرده است.
**از این به بعد همین کلید، کلید دائمی برنامه است** و همهٔ بیلدهای بعدی خودکار با آن امضا می‌شوند.

قواعد ساده (فقط همین ۴ مورد):

1. **هیچ کاری لازم نیست بکنید.** کلید الان در مخزن شماست؛ بیلد بعدی خودش آن را پیدا و استفاده می‌کند
   (در لاگ باید ببینید: `Using persisted CI keystore` و دیگر پیغام «First build: generating...» نیاید).
2. **موقع آپلود سورس جدید، مخزن را حذف یا از نو نسازید.** فایل‌ها را روی همان مخزن فعلی آپلود کنید
   (دکمهٔ Add file → Upload files). آپلودِ روی مخزن، فایل‌های قبلی مثل کلید امضا را پاک نمی‌کند.
   فایل `.github/ci-keystore.jks.b64` را هم هرگز دستی حذف نکنید.
3. **یک پشتیبان بگیرید (۳۰ ثانیه):** در گیت‌هاب فایل `.github/ci-keystore.jks.b64` را باز کنید →
   دکمهٔ Download raw file → فایل را جای امن (مثلاً ایمیل خودتان) نگه دارید. اگر روزی مخزن را از نو
   ساختید، همین فایل را در همان مسیر آپلود کنید تا امضا ثابت بماند.
4. **کاربران نسخهٔ ۱.۲.۰ فقط همین یک‌بار** برنامه را حذف و نسخهٔ ۱.۲.۱ را نصب می‌کنند (تعویض امضا در
   اندروید بدون حذف ممکن نیست). از ۱.۲.۱ به بعد، همهٔ آپدیت‌ها — از جمله آپدیت داخلی خود برنامه —
   بدون حذف و روی نسخهٔ قبلی نصب می‌شوند.

نکتهٔ جانبی: از نسخهٔ ۱.۲.۱ بیلد محلی (لپ‌تاپ) هم به‌صورت خودکار از همین فایل استفاده می‌کند؛ پس خروجی
Android Studio شما هم همان امضای CI را دارد.

توجه امنیتی: کلیدی که داخل مخزنِ عمومی است فقط «آپدیت‌پذیری» را حل می‌کند نه «اصالت» را (هر کسی
می‌تواند APK هم‌امضا بسازد). اگر روزی خواستید به کلید خصوصی (Secrets یا `keystore.properties`)
مهاجرت کنید، امضا عوض می‌شود و کاربران باید یک‌بار دیگر حذف/نصب کنند — این کار را برای یک نسخهٔ
بزرگ نگه دارید و در متن ریلیز اطلاع دهید.

## هشدار Google Play Protect هنگام نصب («App blocked to protect your device»)

این هشدار مخصوص برنامه‌هایی است که خارج از گوگل‌پلی نصب می‌شوند و **گواهی امضای آن‌ها برای گوگل ناشناخته** است. ریشهٔ مشکل در بیلدهای قبلی این پروژه، همان **امضای debug** بود: کلید debug روی هر سیستم/رانر CI به‌صورت خودکار و متفاوت ساخته می‌شود؛ یعنی از دید گوگل «هر نسخه = یک توسعه‌دهندهٔ ناشناس جدید» و هشدار هر بار نمایش داده می‌شد.

از این نسخه (بدون تغییر شمارهٔ نسخه):

1. بیلد Release **هرگز** با کلید debug امضا نمی‌شود؛ اگر Keystore پایدار موجود نباشد، بیلد با پیام خطای واضح متوقف می‌شود (دیگر هیچ fallback بی‌صدایی وجود ندارد).
2. امضا با هر سه طرح **v1 + v2 + v3** انجام می‌شود (v3 در حالت پیش‌فرض AGP خاموش است).
3. ورک‌فلو CI قبل از انتشار، امضای همهٔ APKها را با `apksigner` بررسی می‌کند؛ اگر APK بدون امضای v2 باشد یا با گواهی debug امضا شده باشد، انتشار متوقف می‌شود.

### نکتهٔ مهم دربارهٔ اعتبار گواهی

اعتبار (reputation) گواهی نزد Play Protect به‌مرور و سمت سرور گوگل ساخته می‌شود. با **کلید ثابت**، پس از نصب‌های اول این هشدار برای کاربران بعدی حذف می‌شود — دقیقاً همان اتفاقی که برای پروژه‌های مشابه گیت‌هابی افتاده است (کلید ثابت + زنجیرهٔ امضای کامل، بدون انتشار در گوگل‌پلی). دو قانون طلایی:

- **هرگز کلید امضا را عوض نکنید.** تعویض کلید = شروع دوبارهٔ هشدار برای همهٔ کاربران.
- فایل `.github/ci-keystore.jks.b64` (یا Keystore خصوصی خودتان) را همیشه حفظ و از آن پشتیبان بگیرید.

## نصب مستقیم ۱.۲.۲ روی ۱.۲.۱ (Over-install) — تضمین‌شده ✅

این بخش مربوط به الزام نسخهٔ **۱.۲.۲** است: کاربر باید بتواند بدون حذف نسخهٔ ۱.۲.۱،
نسخهٔ جدید را مستقیماً روی آن نصب کند و تمام تنظیماتش حفظ شود.

### اندروید چه چیزی را چک می‌کند؟

برای اینکه نصب روی نسخهٔ قبلی موفق باشد، هر سه شرط زیر باید برقرار باشند:

| شرط | وضعیت در ۱.۲.۲ |
|---|---|
| `applicationId` یکسان | `studio.cluvex.aether` — **تغییر نکرده** |
| گواهی امضای یکسان (همان زنجیرهٔ کی‌استور) | همان کلید رسمی ۱.۲.۱ (حالت `release` — پایین بخوانید) |
| `versionCode` صعودی | از **۵** به **۶** |

### دو حالت امضا در CI (مهم)

بیلد دقیقاً دو حالت دارد و خودش در لاگ اعلام می‌کند در کدام حالت است:

| حالت | چه زمانی | کلید | پین اثرانگشت | قابل نصب روی ۱.۲.۱؟ |
|---|---|---|---|---|
| `release` | سکرت‌های `KEYSTORE_BASE64`، `KEYSTORE_PASSWORD`، `KEY_ALIAS`، `KEY_PASSWORD` در مخزن تنظیم شده باشند | کلید رسمی ۱.۲.۱ | بله، اعمال و سختگیرانه | ✅ بله |
| `test` | مخزن آزمایشی بدون سکرت | گواهی موقت CI | خیر (هرگز کامیت نمی‌شود) | ❌ خیر — فقط تست |

مهم: در حالت `test` هیچ اثرانگشتی در `.github/expected-signer.txt` ذخیره نمی‌شود.
بنابراین بیلد گرفتن در یک مخزن آزمایشی **هرگز** امضای مخزن اصلی ۱.۲.۱ را خراب نمی‌کند.
وقتی پروژه را در مخزن اصلی آپلود کردید، کافی است همان چهار سکرت کلید ۱.۲.۱ تنظیم باشند
تا خروجی دقیقاً با همان امضا ساخته شود و نصب روی ۱.۲.۱ بدون حذف انجام شود.

### شماره‌گذاری نسخه در ۱.۲.۲

```
versionCode = 6      // 1.2.1 برابر 5 بود
versionName = "1.2.2"
```

به‌دلیل ABI Split، شمارهٔ نهایی هر APK با فرمول `versionCode * 1000 + offset` ساخته می‌شود:

| ABI | offset | ۱.۲.۱ | ۱.۲.۲ |
|---|---|---|---|
| `armeabi-v7a` | 1 | 5001 | **6001** |
| `arm64-v8a` | 2 | 5002 | **6002** |
| `universal` | 3 | 5003 | **6003** |

هر سه مقدار اکیداً بزرگتر از معادل خود در ۱.۲.۱ هستند، پس اندروید آن را یک **ارتقا** می‌بیند
و نه یک تنزل (downgrade با خطای `INSTALL_FAILED_VERSION_DOWNGRADE` رد می‌شود).

> فاصلهٔ ۵ → ۷ عمدی است: شمارهٔ ۶ برای بیلدهای داخلی/هات‌فیکس احتمالی میان دو نسخه کنار گذاشته شده است.

### گیت جدید CI: پین کردن اثر انگشت امضاکننده

در ۱.۲.۱ تنها بررسی می‌شد که APK با کلید debug امضا نشده باشد. این کافی نیست: یک کلید
ریلیزِ **متفاوت** هم از این بررسی عبور می‌کرد و درست همین موضوع ریشهٔ «مشکل امضا» بود.

در ۱.۲.۲، مرحلهٔ **Verify release signature** در `.github/workflows/build.yml` این کار را انجام می‌دهد:

1. با `apksigner verify --print-certs` اثر انگشت **SHA-256** گواهی امضاکننده را از تک‌تک APKها استخراج می‌کند.
2. آن را با مقدار مرجع در **`.github/expected-signer.txt`** مقایسه می‌کند.
3. در صورت عدم تطابق، **بیلد با خطا متوقف می‌شود** و هیچ ریلیزی منتشر نمی‌شود.
4. اگر این فایل وجود نداشته باشد (فقط اولین بیلد)، مرحلهٔ **Pin signer fingerprint** اثر انگشت فعلی را
   می‌نویسد و خودکار کامیت می‌کند (فقط روی شاخه، نه روی تگ).

به زبان ساده: **از این پس اگر کلید امضا به هر دلیلی عوض شود، به‌جای اینکه کاربر هنگام نصب با خطای
«App not installed» مواجه شود، خود بیلد شکست می‌خورد.**

### بررسی دستی پیش از انتشار

```bash
# اثر انگشت نسخهٔ قدیمی و جدید باید کاملاً یکسان باشند
apksigner verify --print-certs Aether-1.2.1-universal.apk | grep -i 'SHA-256 digest'
apksigner verify --print-certs Aether-1.2.2-universal.apk | grep -i 'SHA-256 digest'

# مقدار پین‌شده در مخزن
cat .github/expected-signer.txt
```

و برای تست واقعی نصب روی نسخهٔ قبلی (بدون حذف):

```bash
adb install -r Aether-1.2.2-arm64-v8a.apk
```

خروجی باید `Success` باشد. در صورت مشاهدهٔ `INSTALL_FAILED_UPDATE_INCOMPATIBLE` یعنی کلید امضا عوض شده است
— در این حالت APK را منتشر نکنید و ابتدا کی‌استور را به حالت قبل برگردانید.

### دادهٔ کاربر چه می‌شود؟

پروفایل در DataStore با نام `aether_profile` ذخیره می‌شود و در نصب روی نسخهٔ قبلی دست‌نخورده باقی می‌ماند.
کلید جدید `location` که در ۱.۲.۲ اضافه شده، در پروفایل‌های قدیمی وجود ندارد و به مقدار پیش‌فرض
(رشتهٔ خالی = حالت خودکار) فرومی‌افتد؛ پس مهاجرت داده لازم نیست و رفتار برنامه برای کاربران
ارتقایافته دقیقاً مانند قبل است تا زمانی که خودشان یک کشور را انتخاب کنند.
